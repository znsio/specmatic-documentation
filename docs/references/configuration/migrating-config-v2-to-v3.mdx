# Migrate an existing configuration to V3

Keep the original file, convert into a new file, then check the behavior you depend on. V3 separates the tested service (`systemUnderTest`) from mocked dependencies (`dependencies`). Reusable `components` are optional; the upgrader can produce inline definitions.

This journey ran against OSS 2.55.3 and Enterprise 1.28.3 using local OpenAPI specifications and explicit test/mock endpoints. It is a bounded migration check, not a promise that every legacy setting or protocol has identical behavior after conversion.

Save these files together in a fresh demonstration directory. You need the [Docker setup](/references/configuration/local-openapi#docker-setup), Node 20+ for the demonstration target, and free ports 9100/9101. Run commands beside the config so the local source paths agree.

## 3. Review the changes

- **Tested specs:** `contracts[].provides` becomes definitions inside `systemUnderTest.service`. Check that the same specifications are tested.
- **Mocked specs:** `contracts[].consumes` becomes definitions inside each dependency service. Check that the same specifications are mocked.
- **Sources:** the local directory moves into each definition's `source.filesystem`. Check that its spec paths still find the supplied contract.
- **Endpoints:** entry-specific test URL and mock host/port become overrides under `runOptions.openapi.specs`. Check that each override targets the generated `books` ID.
- **Reports:** `test.junitReportDir` becomes `junitReportDir` inside `specmatic.settings.test`. Check that JUnit output still lands in `reports`.
- **Watcher setting:** `stub.hotReload: disabled` becomes `hotReload: false` inside `specmatic.settings.mock`. Check that the intended setting is retained.

The `books` ID joins the definition to its run-option override. If you rename an ID, update both places; see [spec identity and overrides](/references/configuration/spec-overrides). Generated IDs can change when you add colliding spec filenames, so review the actual output rather than assuming an ID convention.

The output need not contain `components` or explicit `type` fields for this selected test/mock context. You can [reuse components](/references/configuration/component-references) later; adding them is not a migration prerequisite.

For your own file, also review example/dictionary selection, credentials and certificates, hooks/adapters, filters, resiliency, reports and CLI/environment overrides. Conversion binds and serializes the configuration model: it is not a formatting-preserving editor and does not promise to retain comments or every extension field. Keep the original for comparison. See [paths](/references/configuration/files-and-paths), [data selection](/references/configuration/data-selection) and [test target precedence](/references/configuration/test-targets).

## Other legacy configurations

The upgrade command also accepts V1 input, but this before/after journey covers V2 OpenAPI with a local source. Remote/private sources, other protocols and additional legacy settings need their own comparison checks. Do not move source files or change targets at the same time unless you intentionally want those behavior changes.

For discovery and command options, see [Upgrade Configuration](/references/configuration/upgrade-specmatic-config). For new files, start with the [V3 task guide](/references/configuration).
