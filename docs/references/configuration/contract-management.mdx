# Choose where your specifications come from

<span id="versions-3---systemundertest-and-dependencies" />

Each selected service has `definitions`. A definition chooses **one source** and the `specs` to load from it. Inline sources and references to `components.sources` use the same provider shapes.

| Specs live… | Select | Spec paths refer to… |
|---|---|---|
| In a local folder | `filesystem` | Files inside its `directory` |
| At an HTTP(S) base URL | `web` | Paths appended to that base URL |
| In a separate Git repository | `git` with `url` | Files inside the selected checkout |
| In your current Git checkout | `git: {}` | Files relative to the config location in the checked monorepo loader |

These examples ran against OSS 2.55.3 and Enterprise 1.28.3 using core OpenAPI mocks. Source-model rules below are separate from protocol-specific consumers; the recipes do not establish every protocol or integration's loading behavior.

The same request now returns `Alternate Handbook`, proving that the selected branch changed the loaded contract. The template's `main` default is authored in this demonstration; it is not Specmatic's universal branch default.

For a remote repository, supply your clone URL through `CONTRACTS_REPOSITORY` and select its real branch and spec paths. The checked Git loader can use a bundled checkout, a same-named checkout under the home `.specmatic/repos`, or a local checkout under the run's `.specmatic/repos`; those branches of loading can behave differently. Review loading logs and the actual contract before assuming a branch change refetched a pre-existing checkout. These recipes establish local-URL cloning and explicit branch selection, not private-host authentication or every cache-refresh case.

With no explicit branch and no branch matching, cloning uses the repository default. `matchBranch: true` or the applicable CLI match-branch input asks for the current branch; GitHub Actions lookup considers `GITHUB_HEAD_REF`, then `GITHUB_REF_NAME`, then the local Git branch. Failure to determine it falls back to the configured branch. Checkout exceptions can be caught and logged only at debug level; confirm the branch/content instead of treating startup as proof of selection. Those additional cases are source traced, not established by the two branch recipes.

`git.auth` selects one of `bearerFile`, `bearerEnvironmentVariable` or `personalAccessToken`. The latter is a token value, not a filename. Authentication applies to Git access, separately from API authentication. Do not commit credential values in example defaults; private-host transport verification remains outside this recipe.

## Reuse sources and validate

Declare a source under `components.sources.<yourName>` and select it from a definition with `$ref: '#/components/sources/<yourName>'`. Declaration alone does not choose specs or start a service. See the [complete component-reference recipe](/references/configuration/component-references), and [spec IDs](/references/configuration/spec-overrides) when selecting multiple specs.

With the source server available and the files inside a Git checkout, validate the six non-templated working forms:

<CodeBlock language="terminaloutput">{require('./includes/source-recipes/validate.terminaloutput?raw').trimEnd()}</CodeBlock>

Validation and runs can read/download specifications and write caches. Validate the templated Git file with its URL input supplied; an unresolved or empty default URL is not a working repository selection. The browser does not fetch specs or verify credentials and reachability.
