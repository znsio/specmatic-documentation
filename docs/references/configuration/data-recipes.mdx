# Run examples and dictionary recipes

These complete OpenAPI mock recipes demonstrate **which example is returned and which dictionary supplies generated values**. They use the same inputs and response assertions tested against OSS 2.55.3 and Enterprise 1.28.3.

## Save the inputs

Follow the [Docker setup](/references/configuration/local-openapi#docker-setup). Save the files below in one folder, run commands there, and keep port **9101** free. Stop each mock with Ctrl+C before starting the next scenario.

```text
.
├── orders.yaml
├── service-data.yaml
├── shared-data.yaml
├── empty-examples.yaml
├── extra-only.yaml
├── combined-data.yaml
├── data/
│   ├── shared.yaml
│   └── service.yaml
└── examples/
    ├── common/order.json
    ├── service/order.json
    └── environment/order.json
```

`/orders/{id}` can return an external example. `/generated` has no authored example, so its response demonstrates dictionary-driven generation. The contract has no inline examples.

## Additional directories: check the actual result

In these released CLI mocks, an additional directory supplied through `--examples` or `EXAMPLE_DIRECTORIES` loads when no configured example directories contribute examples. With the configured service/common examples in this recipe, the additional directory is bypassed. The loader can take the configured/implicit-example branch before its fallback to the additional directory.

**To reliably add a directory alongside configured examples, include it in `data.examples`.** A directory appearing in a config accessor's list does not prove that the mock loader used it.
