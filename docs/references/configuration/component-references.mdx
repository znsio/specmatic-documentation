# Reuse components and understand reference overrides

Use `components` to declare reusable sources, services, run options, settings or data. A declaration alone does not start a mock or select a test service: select it from the operation's use site. The target must fit the type expected there.

These examples ran against OSS 2.55.3 and Enterprise 1.28.3. They check local source/service references, service sibling overrides and relative external-source failure and recovery; they do not establish every protocol or external-reference combination.

## Siblings replace matching properties

A sibling property beside `$ref` replaces the same property on the target. This is a **shallow** combination: a sibling `settings` object replaces the referenced service's whole `settings` object. It does not preserve omitted nested values.

## Local references use literal map segments

For local `#/components/...` refs, the checked resolver traverses map keys literally. It does not decode `~1` or `~0`, and it does not traverse array indexes. Use simple component names; do not copy an inspector location pointer into a configuration reference without checking it.

<summary>array-target.yaml — unsupported array traversal</summary>

This exits with code 1: `definitions/0` cannot be reached through this local map resolver. Recover by referencing the whole service component. A missing target, including a null destination, is unresolved. External references are handled by a different resolver; do not apply these local map rules to every external URI fragment.

If a reference fails, check the use-site type, exact destination, supported traversal and sibling replacements, then rerun validation and the intended operation.
