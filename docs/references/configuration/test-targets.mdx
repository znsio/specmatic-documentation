# Choose a test target across environments

For a V3 OpenAPI test, set `systemUnderTest.service.runOptions.openapi.baseUrl`, or use `host` and `port`. Use a [configuration template](/references/configuration/template-values) when the same file should select a different target in CI or another environment.

These recipes cover configuration-driven core HTTP tests in OSS 2.55.3 and Enterprise 1.28.3. Direct contract-path arguments, JUnit integrations and other protocols can select targets differently.

Save these files together. You need Node 20+, Java, the [Docker setup](/references/configuration/local-openapi#docker-setup), and free ports 9000, 9100 and 9102 for the demonstration. Run beside the files.

This selects HTTP on 9102. Without `baseUrl`, the service model needs `port` to construct an endpoint; `host` alone is insufficient. An omitted host with a configured port uses `localhost`. Use `baseUrl` for an explicit scheme or URL path.

The runner loads specification targets from the file separately from its fallback settings. A CLI base URL is staged, but it does not reroute the file-loaded service endpoint in these releases. [Per-spec targets](/references/configuration/test-spec-overrides) have a similar checked boundary. Check the actual receiving URL; a passing test alone does not prove that an override took effect.

Explicit CLI host/port can supply the next fallback when there is no selected base URL. The CLI host defaults to `localhost`; its port defaults to 0 when not supplied. Prefer a full URL or specify both host and port.

<CodeBlock language="terminaloutput">{require('./includes/test-targets/template-target.terminaloutput?raw').trimEnd()}</CodeBlock>

This resolves the file's target to **9102** before it is loaded. Without `BOOKS_TARGET`, the authored default is 9100. The template can also read a same-named JVM property; environment values win. Keep numeric ports numeric by templating the whole run-options object when needed; see the [template guide](/references/configuration/template-values).

## Invalid fallback values can still stop a configured run

<CodeBlock language="terminaloutput">{require('./includes/test-targets/invalid-environment.terminaloutput?raw').trimEnd()}</CodeBlock>

This intentional failure exits with code 1 before sending the book request. The runner checks its fallback URL even though the file has a configured endpoint. Remove the invalid `testBaseURL` input and rerun `configured.yaml`; do not leave conflicting unused inputs in the process environment.
