# Test specs against separate targets

Use spec IDs when one tested service's definitions need different API targets. The ID in each declaration joins to the matching entry under `runOptions.openapi.specs`. See [spec IDs and mock overrides](/references/configuration/spec-overrides) for the two-list structure and matching rules.

These examples ran against OSS 2.55.3 and Enterprise 1.28.3. They demonstrate core OpenAPI CLI testing; other protocol runners have their own target options.

## CLI base URL and configured per-spec targets

Keep the targets running and use the matched configuration:

<CodeBlock language="shell">{require('./includes/spec-test-overrides/test-cli.sh?raw').trimEnd()}</CodeBlock>
<CodeBlock language="terminaloutput">{require('./includes/spec-test-overrides/test-cli.terminaloutput?raw').trimEnd()}</CodeBlock>

Both tests still reach their configured per-spec targets on 9100 and 9102, although the CLI argument supplies 9103. The CLI stages a service-level base URL, but the configuration-driven runner loads specification targets from the file separately; each selected spec already has its own endpoint. Do not assume this flag reroutes every spec. To reroute one of these specs, edit its matching override. A spec without its own endpoint can use the service-level endpoint from the file. See [test target selection](/references/configuration/test-targets) for the separate configured-target and CLI-fallback cases.

This is scoped to the checked configuration-driven CLI run. Passing contract paths directly or using another integration can select targets differently.

The declaration's `urlPathPrefix: /v2/` appends `v2` to the selected authors base URL. The contract path remains `/authors/1`, producing a request to **9102/v2/authors/1**. Books stays on **9100/books/1**. Leading/trailing slashes on the prefix are trimmed; a missing, empty or slash-only prefix adds no path. The checked recipe demonstrates HTTP test request routing; it does not prove that a mock rewrites contract paths the same way.

Stop the demonstration targets when finished. If a test goes to the wrong place, check the exact spec ID, the selected protocol options, per-spec endpoint versus service fallback, and any authored prefix before changing timeouts or response examples.
