# Test a Kafka service with AsyncAPI

Test a running application's messages against its AsyncAPI contract. These V3 examples were checked with **Enterprise 1.28.3**. Specmatic sends a ping, receives the application's pong, and checks its payload. An incorrect reply fails the test.

## Prepare the local demo

Follow the [Docker setup](/references/configuration/local-openapi#docker-setup), configure your [license](/enterprise_onboarding/license_key), and use a fresh directory. The optional demo needs **JDK 17+** and the downloaded Enterprise executable JAR. Set `SPECMATIC_ENTERPRISE_JAR` to that JAR's absolute path in the demo terminal. Port **19096** must be free.

Save `asyncapi.yaml` and `test.yaml`:

<CodeBlock language="yaml" title="asyncapi.yaml">{require('./includes/async-kafka-test/asyncapi.yaml?raw').trimEnd()}</CodeBlock>
<CodeBlock language="yaml" title="test.yaml">{require('./includes/async-kafka-test/test.yaml?raw').trimEnd()}</CodeBlock>

`systemUnderTest` selects the service to test. The runtime server is `external`: the test connects to the broker started separately by your application or the demo. This test config does not start a broker. Keep the document's server endpoint aligned with the runtime server for this release; the initial broker check has the limitation described below.

Use your matching implementation, or save `KafkaService.java`. This small independent demo starts a loopback Kafka broker and replies to ping messages. It uses Apache Kafka/Curator/Jackson libraries packaged in the executable JAR; it does not run a Specmatic message mock. Broker data is created in a new temporary directory and removed on normal shutdown. It is a local demonstration, not a production Kafka deployment.

## Keep both broker endpoints aligned

In this release, the initial availability check uses the **document's** server endpoint. A runtime config pointing to the healthy broker does not replace that endpoint for the initial check.

## Reply timeout limitation

The released CLI request/reply runner passes a fixed **10,000 ms** message wait to its scenario. Although the config DTO reads `replyTimeout` and the CLI accepts `--reply-timeout`, these values do not replace that wait in this checked entry point.

## Subscriber readiness limitation

For this CLI runner, the first scenario's timeout object is created **before** that scenario's config is applied. Its readiness wait therefore comes from the CLI-initialized JVM property. The Kafka client waits for its subscription latch, then applies this additional delay; the delay does not start or verify your application's subscriber.

<CodeBlock language="shell">{require('./includes/async-kafka-test/readiness-cli.sh?raw').trimEnd()}</CodeBlock>

Use `--subscriber-readiness-wait-time` for this checked first-scenario CLI setup. Do not infer a reliable per-scenario config delay: the runner changes JVM properties after constructing the timeout object, which may affect later scenarios. Multi-scenario timing and other bindings/integrations still need separate verification. Per-spec mock options reject both `subscriberReadinessWaitTime` and `replyTimeout`; neither is a mock response-delay setting.
