# Template values in V3 configuration

Use templates when the same configuration needs a different specification path, endpoint or settings object in another environment. Keep `version: 3` literal. This page describes OSS 2.55.3 and Enterprise 1.28.3 configuration loading; [example-file templates](/features/external_examples) have separate rules.

## Syntax and lookup

Quote a template in YAML so the YAML parser treats it as a string:

```yaml
# A whole value
baseUrl: '{API_URL:http://127.0.0.1:9100}'
# An embedded value
baseUrl: 'http://{API_HOST:127.0.0.1}:9100'
```

These are placement fragments. Use the complete file below for a runnable setup.

Both `{NAME:default}` and `${NAME:default}` are supported. The colon is required; `${NAME}` and `{NAME}` remain literal text. A default can be empty: `{NAME:}`.

For one name, Specmatic uses:

1. The environment variable, if present.
2. The Java system property of the same name, if present.
3. The authored default.

An empty environment value is present and suppresses both the property and default. Defaults belong to the template you wrote; they are not necessarily the default for that configuration key. Values are resolved recursively inside configuration objects and lists, but **map keys are literal**: a component named `{NAME:books}` keeps that name.

## Whole values and embedded values

A whole-value template can supply an object or array. Use valid JSON for a portable, readable structured value. A JSON-quoted string is decoded as a string; ordinary scalar results remain text at the template-resolution stage. An embedded template always produces a string, even when its replacement resembles JSON.

This matters for typed fields. A numeric string can bind during a mock run while failing the stricter resolved-schema validation. The checked recipe below uses a literal numeric port and a whole settings object containing real booleans. To parameterize a typed number or boolean while retaining schema validity, supply its enclosing object as structured JSON, for example:

Malformed structured replacements remain strings when parsing fails; a field requiring an object then fails validation/binding. Template resolution does not recursively expand tokens introduced by a replacement. Avoid putting secrets in defaults or printing resolved credentials.

### Multiple names: a release limitation

Embedded `{FIRST|SECOND:default}` checks each name in order, using that name's environment value before its system property. However, a **whole-value** `{FIRST|SECOND:default}` currently uses only `FIRST` or its default. A missing first name does not fall through to `SECOND` in the releases above. Prefer a single name for whole values.

Whole-value detection also takes precedence over embedded detection. Avoid a string that starts with one bare token and ends with another, such as `{FIRST:a}-{SECOND:b}`; it can be interpreted as one whole-value expression. Use a literal prefix/suffix, such as `prefix-{FIRST:a}-{SECOND:b}`, when combining embedded tokens. These boundaries were checked directly against both released template resolvers.

Save `structured-options.yaml` from the expanded variant above too. In a fresh shell with the example variables absent, validate both complete configurations:

<CodeBlock language="terminaloutput">{require('./includes/template-recipes/validate.terminaloutput?raw').trimEnd()}</CodeBlock>

Configuration validation resolves values in **that process's environment**, checks the resolved schema and supported semantics, and loads selected specification sources. Remote sources can therefore be fetched or cached. Validation does not prove that a mock serves the expected responses.
