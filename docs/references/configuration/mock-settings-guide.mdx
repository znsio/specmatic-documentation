# Choose mock settings and understand their scope

Mock settings have two scopes: **request behavior can be selected per service; lifecycle settings apply to the whole core mock runner.** This guide covers core HTTP mocks in OSS 2.55.3 and Enterprise 1.28.3. Other protocol runners and Studio can consume settings differently.

## Where values come from

<div className="configuration-settings-summary">

| Setting | Core consumer scope | Omitted value / fallback |
|---|---|---|
| `strictMode` | Request handling can use service → dependency → global; startup/loading also uses dependency → global | `SPECMATIC_STUB_STRICT_MODE`, environment before JVM property; otherwise false in these consumers |
| `generative` | Service → dependency → global | false; does not disable ordinary generated success responses |
| `delayInMilliseconds` | Service → dependency → global, unless the expectation supplies its own delay | `SPECMATIC_STUB_DELAY`, environment before JVM property; otherwise no configured delay |
| `lenientMode` | Selected service's parser mode, unless the source entry supplies one | false in core loading; no V3 mock environment/property fallback |
| `startTimeoutInMilliseconds` | Dependency → global | 20,000 ms in the lifecycle accessor |
| `hotReload` | Dependency → global, then CLI watcher choice | Enabled by the core CLI when omitted |
| `gracefulRestartTimeoutInMilliseconds` | Dependency → global, then CLI server stop | 1,000 ms in the core CLI |

</div>

Settings merge **field by field**. Overriding delay does not discard inherited generative or lenient values. Explicit `false` and `0` are retained; omission falls back. Lifecycle accessors do not consult individual service settings, even though those keys are structurally accepted in a service settings object.

Use dependency-wide settings for startup, watcher and shutdown choices. Use service settings for request behavior that should differ between services.

## CLI strictness and service strictness can differ

Stop the mock and run the relaxed configuration with the CLI flag:

<CodeBlock language="shell">{require('./includes/mock-settings/cli-strict.sh?raw').trimEnd()}</CodeBlock>

`/books/2` still returns a generated HTTP 200 response. The core CLI flag sets dependency-level strictness for startup/loading and fallback use; the service's explicit `strictMode: false` remains selected for its request handling. If you want that service to use strict request behavior, set its value to true or remove its false override.

## Lifecycle and parsing: avoid the wrong expectation

- **Startup timeout:** put it at dependency/global scope. It bounds particular startup/readiness waits, not every phase of the command or a whole test suite. CLI readiness can perform multiple waits using the selected timeout.
- **Hot reload:** the core CLI defaults to enabled. Dependency `hotReload: false` disables its watcher in these recipes. CLI `--hot-reload enabled/disabled` controls the CLI choice. The watcher is registered for contract paths and CLI example directories; this does not establish that every referenced config/data file is watched.
- **Graceful restart:** the core CLI uses the selected dependency/global value for server stop, with `--graceful-restart-timeout-in-ms` taking priority. It is a shutdown grace period, not an extra delay before the new server becomes ready.
- **Leniency:** source-entry parsing mode, including CLI `--lenient`, can override service configuration. It applies to selected parser recovery paths. It does not disable all validation or make every broken contract usable; strictness and leniency are independent.

The recipes verify request strictness, normal generation with generative false, service delay and the shown CLI interactions. Watch/restart timing, startup failure timing, lenient recovery and generative invalid-request variants still need their own effect checks. Read each key's scoped explanation in [All V3 Configuration Keys](/references/configuration/all-keys), or explore its placement in the [Configuration Explorer](/references/configuration/explorer).
