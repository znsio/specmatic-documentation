# Check OpenAPI changes against a Git baseline

Use `specmatic.settings.backwardCompatibility` to choose the repository, baseline and changed files checked by `specmatic backward-compatibility-check`. This recipe was checked with **OSS 2.55.3 and Enterprise 1.28.3**. It needs Git and Docker with the `specmatic/enterprise` image; it does not start an API or mock.

The command compares Git states, not the specs declared under `systemUnderTest` or `dependencies`. It can switch branches and stash/restore local changes while reading both versions. The demo below uses a separate new repository with committed inputs. Save and review changes before applying the command to your own repository; restoration with uncommitted/conflicting changes is outside this recipe's checks.

## Understand the four settings

| Setting | Omission and use |
|---|---|
| `baseBranch` | Uses the current branch's upstream when configured, otherwise the current branch. Set an explicit baseline to avoid an accidental self-comparison. CLI `--base-branch` wins. |
| `repoDirectory` | Defaults to the command's working directory (`.`). The checked relative value `contracts-demo` is also process-relative. CLI `--repo-dir` wins. |
| `targetPath` | Defaults to no narrower path filter. It filters changed file paths; it does not select service definitions or fetch sources. CLI `--target-path` wins. |
| `strictMode` | Defaults to `false`. Controls usage-aware Insights verdicts; it does not enable ordinary schema validation or make a basic breaking change safe. CLI `--strict` wins. |

In the reviewed consumer, `targetPath` is a path-substring filter, not a glob or a guaranteed exact-file match. Choose a specific path that distinguishes your intended files. The strict-versus-lenient Insights result needs a configured usage service and is not demonstrated by this local demo.
