# Identify specs and override their run options

A service can load several specifications. Give a specification an `id` when you want to target it from `runOptions.<protocol>.specs`. The two lists have different jobs:

- `definitions[].definition.specs` selects the specification files.
- `runOptions.openapi.specs` selects overrides for already selected files, by ID. It does not load additional files.

This guide checks OpenAPI mocking against OSS 2.55.3 and Enterprise 1.28.3. Other protocol overrides and test targets need their own supported fields and execution checks.

## Matching rules and fallback

IDs match exactly, including case. They are local joins to a service's run-option list; they are not filenames or CLI aliases. A plain string specification path has no ID. An object specification can omit its ID when it needs no ID-based override.

If there is no matching override, the spec uses the service's protocol run options. When duplicates match, the **first** override wins. Avoid duplicates rather than relying on ordering.

Endpoint selection is not a field-by-field merge:

1. A matching override's `baseUrl` supplies the endpoint when present, taking priority over its `host` and `port`.
2. Otherwise an override needs `port` to supply an endpoint. Its omitted host defaults to `0.0.0.0` for mock source selection or `localhost` for test source selection; it does not inherit the service's host.
3. An override containing only `host` supplies no endpoint, so endpoint selection falls back to the service run options.
4. The service endpoint likewise prefers its `baseUrl`, otherwise its `host` plus `port`.

The endpoint accessor rules above are source traced. The recipes observe matching, mismatch, duplicate order and `baseUrl` priority in released OpenAPI mocks; they do not establish all test/CLI/protocol precedence or every downstream bind-address behavior. Supplying both host and port explicitly keeps the mock's intended bind address clear.

If an override seems ignored, check its exact ID, its placement under the selected service/protocol, duplicate order, and whether it supplies a complete endpoint. For component-based configurations, follow the service's reference to the run options it actually uses. The [explorer](/references/configuration/explorer) shows component use sites; the [key reference](/references/configuration/all-keys#openapirunoptionspecification-id) shows supported placements and constraints.

For checked two-target tests, CLI base-URL interaction and a per-spec path prefix, see [test specs against separate targets](/references/configuration/test-spec-overrides).
