# Configure HTTPS and client certificates

Use `cert` to give a mock its server identity, or give contract tests a client identity for an mTLS service. These V3 examples use a local OpenAPI contract and were checked with **OSS 2.55.3** and **Enterprise 1.28.3**.

<div className="configuration-settings-summary">

| Your task | Start here |
|---|---|
| Start an HTTPS mock | [Configure its server identity](#start-an-https-mock) |
| Require a client certificate at the mock | [Enable incoming mTLS](#require-a-client-certificate) |
| Test an mTLS service | [Configure the test client's identity](#test-an-independent-mtls-service) |
| Reuse an identity | Use a named certificate component; the [mock example](#start-an-https-mock) shows both forms. |

</div>

**Trust boundary:** the checked mock requires a client certificate when mTLS is enabled, but accepts the independently self-signed demo client. Its reviewed implementation uses an insecure trust manager; this is not a trusted-client CA policy. The core HTTP test client also trusts server certificates and disables hostname verification in the reviewed source. A successful contract test therefore does not establish certificate-chain or hostname validity. HTTP authentication tokens are configured [separately](/features/authentication).

## Save the files and create demo identities

Use a **fresh directory**, Java, the [Docker setup](/references/configuration/local-openapi#docker-setup), OpenSSL supporting `-addext`, curl and Node 20+ for the independent target below. Ports 19120 and 19121 must be free. Run commands from this directory.

Save `greeting.yaml`:

Save this script as `certificates.sh` and run it with `bash certificates.sh`:

<CodeBlock language="shell" title="certificates.sh">{require('./includes/https/certificates.sh?raw').trimEnd()}</CodeBlock>
<CodeBlock language="terminaloutput">{require('./includes/https/certificates.terminaloutput?raw').trimEnd()}</CodeBlock>

This creates separate server and client identities, public PEM certificates, unencrypted demo private keys and password-protected `.pfx` stores under `certificates/`. The certificates last one day. `docs-demo-pass` is a public demo password; use your organization's issued identities and secret mechanism for a real setup. The script refuses an existing `certificates` directory rather than replacing its contents. Exporting the password in the script does not change its parent shell; the example configs use that same public default through [config templates](/references/configuration/template-values).

## Choose the right store settings

| Key | Meaning in this setup |
|---|---|
| `keyStore.file` | Existing private-key store; the mock loader accepts `.jks` and `.pfx`. The test loader also accepts `.p12`. |
| `keyStore.alias` | Identity alias: `demo-server` for the mock, `demo-client` for tests. |
| `keyStore.password` | Password unlocking the private key. |
| `keyStorePassword` | Password opening the store. For these PKCS12 demo stores, use the same password for both. |
| `keyStore.directory` | A different mode: the mock creates/replaces `specmatic.jks` there; the test client reads an existing `specmatic.jks`. Do not point a generating mock at a directory whose existing store you need to keep. |
| `mtlsEnabled` | Incoming client-certificate requirement at the mock; omitted or false does not require a client certificate. |

Store/key passwords default to `forgotten` in the reviewed model if omitted. That does not guess the password of an existing store. Set both explicitly using the supported secret/template mechanism.
