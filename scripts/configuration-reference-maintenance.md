## Verified release and source baseline

The single baseline is [`src/data/configuration/source-manifest.json`](../src/data/configuration/source-manifest.json). Its `runtimeVerification` records the V3 format, checked release coordinates, JAR SHA-256, executable and embedded-core commits, packaged schema SHA-256 and observed version output. `revisions` and `sources` identify the research checkouts separately. No local paths, binaries or credentials are shipped with that record.

Both checked artifacts have exactly the committed resolved V3 schema. OSS 2.55.3 contains core commit `05a98c12`; Enterprise 1.28.3 contains core 2.55.3 from `fa123c52` and executable commit `ccb3f957`. A common core version or schema is not proof of identical behavior. The known broker log-directory release/checkout difference is recorded explicitly. Per-key and recipe evidence remains authoritative for runtime claims; the baseline does not certify untested consumers.

When refreshing, inspect each chosen JAR with `java -jar <jar> --version`, compute its SHA-256, and read `META-INF/MANIFEST.MF`, `io/specmatic/specmatic/core/version.properties` and `config-validation/config-v3-resolved.schema.json` from the archive. Compare the packaged schema to the committed snapshot; record actual values in `runtimeVerification` and review source/release differences. A schema mismatch needs investigation and a snapshot/validator/catalog update, not a substituted hash. These are maintainer checks on provisioned release JARs, not reader setup instructions or ordinary build prerequisites.

`npm run check:config` checks the recorded artifact versions against the site's version constants and research release labels, schema hashes against the committed snapshot, and identified differences against recorded source revisions. It does not reread or download JARs. `check-config-source-drift.js --record` preserves runtime evidence rather than replacing it with checkout metadata; after a release/schema/revision change, those checks require the corresponding baseline evidence to be reviewed and updated. The example wrapper provisions latest releases by default, so always compare its resolved versions to this baseline before attaching new execution evidence. Retain the actual edition/version of every run; do not relabel it to match an older baseline.

## One catalog, distinct kinds of evidence

- `schema-v3.json`: exact source schema snapshot, not an authored-input schema (templates resolve first).
- `behavior.json`: reviewed section behavior, independently maintained. Group notes do not prove every field's defaults or precedence.
- `field-behavior.json`: field-specific effects, omission, precedence, caveats and examples with explicit runner scope and maintainer evidence. These feed both explorer search/details and the readable reference. A source-traced field remains distinct from a behavior-tested recipe.
- `validate-v3.js`: generated non-mutating, offline schema validator; regenerate with `node scripts/build-config-validator.js`. Runtime schema compilation is avoided in the browser.
- `catalog.json`: generated canonical entries, aliases, property constraints and context paths.
- `coverage.json`: per-entry status. Pending field behavior/examples/execution remain explicit; do not turn these into passing statuses merely because a generated page exists.
- `all-keys.mdx`: generated readable, searchable reference. The interactive explorer consumes the same catalog.

The 301 property declarations consolidate to 289 entries: ten additional conditional `type` constraints attach to their existing component-protocol entries, and two true Jackson aliases attach to their canonical entries. CamelCase adapter names remain separate from snake_case hooks because the source does not establish alias normalization.

Placements traverse schema refs, unions, arrays, named maps and conditional protocol branches. They describe possible contexts, not a claim that every variant is simultaneously applicable. Requiredness is local to a branch/object. A named-map placeholder is not a literal YAML key.

## Refresh workflow

1. Select the releases being documented, verify artifact identity and packaged schemas as described above, compare config models/consumers to research sources, and update the manifest's runtime evidence and known mismatches.
2. Review schema/model/accessor/DTO/validator and consumer changes, using the source reference to locate downstream behavior. Update structural snapshot and reviewed explanations. Do not assume a field's presence means runtime support.
3. With sibling repos available, run `node scripts/check-config-source-drift.js ../specmatic ../enterprise`. Investigate differences before recording a new baseline with `--record`; recording itself verifies no behavior.
4. Run `node scripts/build-config-catalog.js`, `node scripts/build-config-validator.js` and `npm run check:config`. Ordinary checks/builds use committed snapshots and need no sibling checkout.
5. Update field-level coverage evidence and shared runnable examples, then run the documented example checks, production build and link/UI checks.
